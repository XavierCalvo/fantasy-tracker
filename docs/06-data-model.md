# Fantasy Tracker — Data Model

## 1. Purpose

This document describes the domain model and persistence model used by Fantasy Tracker.

The initial model is intentionally small and separates:

* Player identity.
* Historical market information.
* Personal tracking information.

This separation allows market history to grow independently from the user's personal decisions.

---

## 2. Domain Model

```text
                         ┌─────────────────┐
```

# 3. PLAYER

`PLAYER` represents the identity and relatively stable information of a football player.

### Fields

| Field         | Type                     | Required | Description                        |
| ------------- | ------------------------ | -------: | ---------------------------------- |
| `id`          | BIGINT                   |      Yes | Internal primary key               |
| `name`        | VARCHAR(255)             |      Yes | Player name                        |
| `team`        | VARCHAR(255)             |       No | Current team                       |
| `position`    | VARCHAR(50)              |       No | Player position                    |
| `external_id` | VARCHAR(100)             |       No | Identifier from an external source |
| `created_at`  | TIMESTAMP WITH TIME ZONE |      Yes | Creation timestamp                 |

### Rules

* `id` is generated by the database.
* `name` cannot be null or blank.
* `external_id`, when present, must be unique.
* `external_id` may be null because a player can exist before external-source synchronisation.

---

# 4. PLAYER_PRICE

`PLAYER_PRICE` represents a historical observation of a player's market price.

A player can have multiple price observations.

### Fields

| Field          | Type                     | Required | Description                           |
| -------------- | ------------------------ | -------: | ------------------------------------- |
| `id`           | BIGINT                   |      Yes | Internal primary key                  |
| `player_id`    | BIGINT                   |      Yes | Referenced player                     |
| `price`        | NUMERIC(15,0)            |      Yes | Player price                          |
| `trend_amount` | BIGINT                   |       No | Numeric price movement when available |
| `trend_type`   | VARCHAR(32)              |       No | Structured FutbolFantasy trend        |
| `captured_at`  | TIMESTAMP WITH TIME ZONE |      Yes | Observation timestamp                 |

### Price

Prices are represented as integer euro amounts.

Decimal precision is not required for the current FutbolFantasy price model.

The Java domain model uses `Long`.

---

# 5. Price Trend

The trend is stored using a structured enum rather than display text.

Current values:

```text
INFLECTION_POSITIVE
ACCELERATING_STRONGLY_UP
ACCELERATING_UP
STABLE_UP
DECELERATING_UP
DECELERATING_STRONGLY_UP

INFLECTION_NEGATIVE
DECELERATING_STRONGLY_DOWN
DECELERATING_DOWN
STABLE_DOWN
ACCELERATING_DOWN
ACCELERATING_STRONGLY_DOWN
```

The enum also contains the corresponding Spanish display description.

The database stores the enum identifier, not the translated display text.

This allows the presentation language to change without modifying historical data.

---

# 6. TRACKED_PLAYER

`TRACKED_PLAYER` represents the user's personal relationship with a player.

It is intentionally separate from `PLAYER`.

A player's team or market price is application data; whether the user is watching, owning or discarding that player is personal tracking data.

### Fields

| Field                 | Type                     | Required | Description                                    |
| --------------------- | ------------------------ | -------: | ---------------------------------------------- |
| `id`                  | BIGINT                   |      Yes | Internal primary key                           |
| `player_id`           | BIGINT                   |      Yes | Referenced player                              |
| `status`              | VARCHAR(32)              |      Yes | Tracking status                                |
| `clause`              | NUMERIC(15,0)            |       No | Release clause                                 |
| `clause_release_date` | DATE                     |       No | Date when the clause becomes relevant/released |
| `notes`               | TEXT                     |       No | Personal notes                                 |
| `created_at`          | TIMESTAMP WITH TIME ZONE |      Yes | Creation timestamp                             |
| `updated_at`          | TIMESTAMP WITH TIME ZONE |      Yes | Last modification timestamp                    |

---

# 7. Tracking Status

Current statuses are:

```text
WATCHING
OWNED
DISCARDED
```

Display descriptions:

| Value       | Meaning        |
| ----------- | -------------- |
| `WATCHING`  | En seguimiento |
| `OWNED`     | En plantilla   |
| `DISCARDED` | Descartado     |

The status is stored as a string rather than a database-specific enum to keep the schema portable and easy to evolve.

---

# 8. Relationships

### Player → PlayerPrice

One player can have many historical price observations.

```text
PLAYER 1 ──────── N PLAYER_PRICE
```

Deleting a player currently cascades to its price history.

### Player → TrackedPlayer

The tracking model currently uses a `ManyToOne` relationship.

```text
PLAYER 1 ──────── N TRACKED_PLAYER
```

This deliberately leaves room for future tracking history or multiple tracking records.

The application currently treats tracking as the user's current state. Whether a strict one-active-tracking-record rule should be enforced will be decided before the tracking API is finalised.

---

# 9. Indexes and Constraints

Current database constraints include:

* Primary key on every entity.
* Unique constraint on `PLAYER.external_id`.
* Foreign key from `PLAYER_PRICE.player_id` to `PLAYER.id`.
* Foreign key from `TRACKED_PLAYER.player_id` to `PLAYER.id`.
* Allowed-value constraint for `trend_type`.
* Allowed-value constraint for tracking status.
* Index on `PLAYER_PRICE.player_id`.
* Index on `TRACKED_PLAYER.player_id`.
* Index on `TRACKED_PLAYER.status`.

---

# 10. Historical Data

`PLAYER_PRICE` is an append-oriented historical table.

Price observations should normally not be overwritten when new market data arrives.

Instead:

```text
09:00 → 10.50M
10:00 → 10.55M
11:00 → 10.65M
12:00 → 10.70M
```

This history will later allow the application to calculate:

* 24-hour variation.
* 3-day variation.
* 7-day variation.
* Velocity.
* Acceleration.
* Trend evolution.

These derived metrics are deliberately not stored in the initial schema.

# 11. Future Evolution

Potential future additions include:

* Player market statistics.
* Historical team/position changes.
* Match performance data.
* Additional fantasy-specific metrics.
* Data-source metadata.
* Data quality indicators.
* Historical tracking state.
* User/account ownership if multi-user support is introduced.

These should only be added when there is a concrete product requirement.

# 12. Source of Truth

The current persistence implementation is defined by:

```text
backend/src/main/resources/db/migration/V1__init.sql
```

The Java entities should remain consistent with this schema.

Once V1 is released against a persistent environment, schema changes must be implemented through new Flyway migrations rather than modifying V1.
